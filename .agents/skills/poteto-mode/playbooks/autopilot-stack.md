### Authorization and native ownership

Use this program only within an actual user grant for its commits, pushes, PRs and merges.
Use native `pr_create` for every PR creation. Apply the installed gh-stack skill for
stack operations. CLI instructions below cover only authorized operations not expressed
by native tools; they never authorize `gh pr create` or `origin pr create` here.
Select writer placement by poteto-mode's Capy task execution contract, not by assuming
that a new agent requires cloud. Keep a live PR owner for its callbacks and local state.
Bot comments do not automatically wake this session. Read them explicitly on relevant
status passes. Follow the actual repository automatic-review policy. When a creation or push owes
a callback to this owner, end the turn for that callback. Never assume bot review completion.

### Autopilot-stack

**You own the stack, never the landing. Hand the operator one linear stack of base-chained PRs to review and land.** **Autopilot-full** holds except for how verified work leaves. Each tick re-reads both installed playbooks, and this one wins where they differ. Do not replace either with remote main or an older published copy. At program start, record the actual installed bundle root, version and catalog identity.

1. **Run Autopilot-full's owners, minus the landing.** Owners report STACK-READY in place of merge-ready. They never rebase onto another branch, trunk included, and never retarget, merge, close a PR, or arm auto-merge, because the root owns the chain's topology and the operator owns the landing. When an item depends on another, its owner branches from that item's branch, not from trunk. Resolve the forge once, the same way Autopilot-full does. One native Capy writer task per PR owns build, first push, a ready PR opened before self-proof, self-proof (gates, CI, receipts), skeptical Bugbot triage per `../references/bugbot-triage.md`, a slop-strip (the bundled `deslop` skill (`/deslop`)), `/no-comments` (the **no-comments** skill), and babysit to green per `playbooks/babysit.md`. Owners parallelize when the work is self-contained. Within about 15 minutes, every owner starts a `decisions.tsv` trail in the durable program record per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Keep the trail where a replacement can read it, and return it in the report. Owners also keep the `children.tsv` of Autopilot-full step 2. Match each subagent's reasoning effort and speed to the job through the central poteto-mode model policy. Explicit settings always win. An unavailable control blocks that role. Do not guess a fallback.
2. **Audit on a real loop.** The root runs an audit tick every hour. With explicit periodic-run authorization, the root arms a native Capy hourly audit schedule, per Autopilot-full step 6. Without it, leave that cadence unarmed. Never leave the cadence to memory or lossy completion notifications, and never arm Cursor `/loop`. At each tick, re-read this installed playbook and Autopilot-full, and audit the operation against that selected contract. Fix record drift during that tick. Probe each owner with a generic liveness or status check. Count only side effects as progress. Treat a lane that passes its expected runtime without a side effect as stuck. Stop it, reconcile its checkout, branch and process ownership, then dispatch a replacement with consolidated context. A timeout alone never admits a second writer. No timeout grants permission for two live writers. Probe all subagents and end the tick per Autopilot-full step 6, including the ketchup catch-up when something the operator should see changed.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's stop, every owner takes an immediate zero-writes hold and reports where it stands.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, and STACK-READY with the exact head SHA when its loop is green. The root verifies per Autopilot-full step 4, with STACK-READY in place of merge-ready, and uses current patch evidence from `playbooks/shipping.md`. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified.
6. **Give the topology one writer.** Owners push only their own branches and report each tip, current base, and intended parent. Only the root rebases or retargets a link, because two writers on one chain undo each other. Read the installed gh-stack skill for topology changes. Create through native `pr_create` with the explicit parent base, and retarget through native PR editing. Append each clean PR in dependency order, with its base set to its parent's branch. Only the root PR targets trunk. Never submit or register the chain through `gt`. An owner takes the root's push as its new base and lease. On a conflict, that owner resolves its own slice for the root to push. Publish a rewritten branch with `git push --force-with-lease` pinned to the SHA last pushed or taken over, and only after an `ls-remote` check. On a push you did not make, stop and report. Never force-push a shared branch.
7. **Absorb drift at the root, then re-verify what moved.** Until landing starts, apply Autopilot-full step 5's trunk test and the same combined post-merge checks from `playbooks/shipping.md` to each link, and rebase the chain bottom-up where those checks call for one. A link's base is its parent, so current patch evidence is parent-to-head, not trunk-to-head, until that link is the bottom. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. A rebase rewrites every SHA above it and voids verdicts at the old SHAs unless the patch-id rule in `playbooks/shipping.md` says the lane result still describes the patch. Anything that is no longer valid goes back through this playbook's step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch-id is unchanged. The countersign rule is unchanged from Autopilot-full. A genuinely new pin, or anything that loosens a gate, raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise. The root never gives or bypasses an approval that the forge enforces.
8. **Deliver the chain, then keep your hands off it.** The deliverable is one linear chain of verified PRs, reviewable bottom-up, every link carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it, with their own clicks or by arming merge-when-ready. Once landing starts, nobody writes to the chain except the post-merge move `playbooks/shipping.md` sanctions, because a second writer breaks a landing in flight. That move still runs the same combined post-merge checks and current patch evidence. A mid-landing problem goes through the root to the operator, and any fix waits for the operator's go.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** catch the operator up per the **ketchup** skill, with links to the stack root and tip, a one-line verdict per link, and anything parked or excluded with the reason.
