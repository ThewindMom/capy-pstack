### Authorization and native ownership

Use this program only within an actual user grant for its commits, pushes, PRs and merges.
Use native `pr_create` for every PR creation. Apply the installed gh-stack skill for
stack operations. CLI instructions below cover only authorized operations not expressed
by native tools; they never authorize `gh pr create` or `origin pr create` here.
Select writer placement by poteto-mode's Capy task execution contract, not by assuming
that a new agent requires cloud. Keep a live PR owner for its callbacks and local state.
Bot comments do not automatically wake this session. Read them explicitly on relevant
status passes. Follow the actual repository automatic-review policy. When a creation or push owes
a callback to this owner, end the turn for that callback. Never assume bot review completion.

### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until your swarm, which never wrote the code, has proven the code that lands.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

A verdict covers one patch and green CI covers one head. Run a full swarm once, at the code-ready head, and again only for new behavior, a redesign, or a large new diff. A rebase, a conflict resolution, or a minor fix gets one verifier at the new head. The patch-id rule in `playbooks/shipping.md` can carry a lane result, and every new head needs its own green CI. Use that playbook's current patch evidence and the same combined post-merge checks. Do not invent a weaker local variant.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` only for authorized view, watch and merge operations that native tools do not express. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One native Capy writer task per PR owns build, the first push, a ready PR opened per `playbooks/opening-a-pr.md`, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical Bugbot triage per `../references/bugbot-triage.md`, a slop-strip (the bundled `deslop` skill (`/deslop`)), `/no-comments` (the **no-comments** skill), a rebase onto current trunk, the babysit loop to green (`playbooks/babysit.md`), and the merge itself once steps 4 and 5 clear it. Match each subagent's reasoning effort and speed to the job through the central poteto-mode model policy. Explicit settings always win. An unavailable control blocks that role. Do not guess a fallback. Verification keeps the resolved swarm-worker effort and speed.

   Open the PR early so CI and bots run alongside the work. The code is ready only after the slop-strip and `/no-comments`, so the full swarm runs on finished code. Then rebase onto current trunk and report the code-ready head SHA before self-proof, so verification runs on the base the patch lands on. It also reports the SHA of each later push that changes the PR's patch. Report merge-ready with the head SHA once self-proof, CI, and babysit are done. Fix rounds stay on that base unless trunk conflicts or breaks CI, because each rebase restarts CI. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. Before the code-ready push, and before a later push that needs a verifier, run the pre-review checks that the repo's AGENTS.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof.

   Assume the owner machine dies. Within about 15 minutes, push the first branch snapshot and start a `decisions.tsv` trail per the **show-me-your-work** skill in the durable program record, not only on that machine. Keep a copy with the reports. After that, push again after every verifiable unit worth keeping (hooks on, a WIP commit is fine). Open the PR before self-proof so the URL, decisions, and checks form a durable trail. As soon as a subagent starts, the owner adds its ID, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. To publish a rebase of the owner's own branch, push with `git push --force-with-lease` pinned to the SHA you last pushed or took over. On any push you did not make, stop and report to the root. Never force-push a shared branch. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own. Many owners at once when PRs are self-contained, with one writer per branch and disjoint files. Cross-PR drift is absorbed by rebase, not by stacking. Only genuinely overlapping work serializes. Sequenced or dependent work is Autopilot-stack, not a private stack inside this program. Self-contained PRs branch straight off trunk, and sequenced work is merge-then-branch.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head SHA. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head. Fan out parallel independent verifiers per the **swarm** skill and aggregate to one verdict. The merge needs a clean verdict from the round whose patch matches the merge-ready head. Audit the receipts in the merge-ready report before the verdict. The lanes re-run the gates at that SHA. Prove the load-bearing behavior live on the real surface the change touches (with the matching control skill, such as `control-cli` or `control-ui` from this bundle, or a named driver where none exists). Audit the diff, distrusting the PR body. Run the audit as two or more review lanes with the full brief. Give each lane one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it. A defect trunk shows without the PR is recorded against trunk and does not gate the PR, but one the PR copies or newly reaches is the PR's own. The live lane is the floor, and a verdict without it is not clean. No merge without the root's clean verdict. When the lanes return, send every proven finding against the PR to the owner in one fix-forward. A defect that a lane filed as a note is a finding. For each behavior finding, ask for a red test that covers every site with the same defect. Where no test can show the defect, ask for a repro receipt instead. Add that defect to the next round's review brief. The new head gets a fresh verdict, except for lane results that stay valid under the patch-id rule in `playbooks/shipping.md`. Never push a fix yourself, because each branch has one writer. Replace a stuck owner only after the stop and reconciliation in step 6.
5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. Merge prep never comes before a round's lanes start. Once those lanes have started, merge prep rebases onto current trunk, reports the new head SHA, and waits for green CI. CI must pass on that head before the merge, and current patch evidence decides whether the round's verdict still holds.

   Right before merging, fetch trunk and run the same combined post-merge checks from `playbooks/shipping.md`. Rebase only when those checks say the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head. A failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Those two results are validation without a rebase. They are not a failed path check, and they do not trigger one. Otherwise merge. A rebase those checks require reports the new head SHA, waits for CI to pass on it, and repeats the same checks. It does not add a separate path check. Once that head is green and its patch-id matches the verdict's under the patch-id rule in `playbooks/shipping.md`, a later trunk move does not force another rebase. A new head voids the verdict unless the patch-id is unchanged. CI must pass on that head before the merge. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work. The owner squash-merges its own PR through the resolved forge only when the grant and this verdict allow it, then returns. A new agent takes the next independent item with consolidated context, per poteto-mode's Capy task execution section. Keep live owners for callbacks and reconcile ownership before a completed role changes agents. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) is that kind of raise. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. A disabled or soft-failed check always comes out, because it stops guarding every case. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on trunk is drift, not a raise. Run an audit tick over all owners every hour. With explicit periodic-run authorization, arm a native Capy hourly audit schedule with a bounded run cap and durable program record. Without that authorization, leave the cadence unarmed and use native task/PR events. Never leave the cadence to memory or lossy completion notifications, and never arm Cursor `/loop`. At program start, record the actual installed bundle root, version and catalog identity. At each tick, re-read this installed playbook and `playbooks/shipping.md`, and audit the operation against that selected contract. Do not replace it with remote main or an older published copy. Fix record drift during that tick, such as an unreported head or an unrecorded agent, by having its owner record it. Drift in the record is not a stall. Probe each owner with a generic liveness or status check, and collect the decision trails. Count only side effects as progress, because status text and summaries can hide a stuck child. Commits, pushes, PR or check deltas, and store reports count. Treat a lane that errors, cannot start a turn, or passes its expected runtime without a side effect as stuck. An owner that has neither pushed nor written a trail row by the first tick is stuck. One waiting on you or the operator is not stuck, so answer it. Stop a stuck agent, reconcile its checkout, branch and process ownership, then dispatch a replacement with consolidated context. No timeout grants permission for two live writers. Do not replace it before that stop lands. The tick judges an owner by the pushed branch and the decision trail that step 2 requires, and it replaces an owner whose agent cannot start a turn only after that reconciliation. Each tick also runs the lane stuck test over the program's agent list, where the platform has one, and over every owner's `children.tsv`. Record each stuck child. Replace it only after confirmed stop or terminal failure and ownership reconciliation. Each replacement that stalls gets the same steps. The root takes both steps when the owner cannot. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep, using the same combined post-merge checks. End the tick only when no delegated work is left, even after the last merge. A tick that changed something the operator should see ends by catching them up per the **ketchup** skill, covering each PR's state and verdict, what merged, countersigns and why, and open operator gates, with links to each PR and the trails. A tick that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Each reports where it stands and keeps its brief until the operator releases them.

**Reply:** catch the operator up per the **ketchup** skill. Cover the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each fresh owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
