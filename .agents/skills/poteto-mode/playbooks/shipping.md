### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

This is the half after `playbooks/babysit.md`. A verdict covers a patch, not its commits, and green CI covers one head. Autopilot-full, Autopilot-stack, and Orchestrate use this playbook's current patch evidence and the same combined post-merge checks. Do not invent a weaker local variant.

**Current patch evidence.** Step 3 is the procedure. Build what each lane ran twice at the verdict SHA and once at the current head when the patches differ only in tests, docs, or lint config. Judge each difference, not each file. Do not reuse a lane result from a dev server.

**Combined post-merge checks.** After every merge, run this same set. Confirm the merged SHA is on trunk. Inspect the new bottom PR's base, head, checks, and patch-id. Do not assume a host retargeted it. Recompute current patch evidence. CI must pass on the head that would land. `git merge-tree` of that head against current trunk must be clean. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head. A failing install means the rebase must repair it. When trunk changed a caller of the patch or a dependency the patch uses, run the patch's checks on the merge result and continue only on a pass. A third rebase past merge prep holds and reports rather than looping.

Use native PR tools for creation, edit, and retarget. CLI commands below cover only authorized view, watch, and merge operations those tools do not express. They never authorize `gh pr create` or `origin pr create`, a blanket force-push, or a merge the grant does not cover. Never require Graphite (`gt`). Publish a rewritten owner branch only with `git push --force-with-lease` pinned to the SHA you last pushed or took over. On a push you did not make, stop and report. Never force-push a shared branch.

1. **Resolve the forge, then verify every PR independently.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for authorized view, watch, and merge operations that native tools do not express. Otherwise stay on `gh` and record the fallback. One subagent per PR, not batched, each an independent Capy verification task at the exact PR head, shared for read-only checks or isolated according to the task execution placement contract when driving a mutable app, each exercising the real surface with the matching control skill (such as the bundled `control-ui` or `control-cli`) against parent versus head. Each returns `PASS`, `PASS+NOTES` or `FAIL` and posts that verdict on its own PR. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict. Match each verifier's reasoning effort and speed to the job through the central poteto-mode model policy. Explicit settings always win. An unavailable control blocks that role. Do not guess a fallback. Verification keeps the resolved swarm-worker effort and speed.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. A verified PR sitting above an unverified one is not landable. Report the ceiling as a PR number and say what breaks the chain. A PR whose branch neither holds nor needs the code below it can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that each verdict still describes the patch.** Record the verdict head SHA, base SHA, and stable `git patch-id` of that PR's base-to-head diff. A rebase or base retarget rewrites SHAs and can silently invalidate a verdict without touching a check. Before landing a PR, compare the recorded patch-id with its current base-to-head patch-id. When the two patches differ only in tests, docs, or lint config, build what each lane ran. Build it twice at the verdict SHA and once at the current head. A difference is noise if the two builds at the verdict SHA also show it, or if it is an embedded commit SHA. Judge each difference, not each file, and report each kind of noise with its files. If only noise differs, that lane's result stays valid, and checks and a review of the change run fresh. Do not reuse a lane result from a dev server or from anything else with no build output. Rerun that lane. Re-verify anything else when the patch changed. When it did not, keep the code verdict but re-run mergeability and CI at the current head. Never use matching commit messages or a green check from an older SHA as a substitute.
4. **Prepare only the bottom PR.** Fetch current trunk. Rebase the lowest verified branch onto the exact trunk tip when the combined post-merge checks say the code that would land was never tested. Push only that branch with the pinned lease above, and retarget only that PR to trunk through native PR editing. Re-run step 3 after the push. Do not retarget, arm, or merge descendants yet.
5. **Land one PR at a time.** If the bottom PR is mergeable now and the grant covers the merge, squash it through the resolved forge. On Origin a plain merge can also merge every PR below the one you name. On GitHub a PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for `state`, `mergedAt`, and `baseRefName`. A merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. If requirements are still running and the user asked for merge-when-ready, arm only that PR. Origin's `--auto` is Origin merge-when-ready. GitHub's `--auto` is GitHub auto-merge. Arm it only when the verdict covers the current head, because it lands whatever head is ready. Wait for that PR to merge before preparing the next one.
6. **Do not read GitHub `autoMergeRequest` as stack readiness.** At most it says GitHub auto-merge was requested for one GitHub PR. It does not prove Origin merge-when-ready is armed, that a descendant is queued, that a patch verdict is current, or that the contiguous stack is safe. Confirm the active forge's state for the current bottom PR, and say that the state is unknown if the active forge cannot report it.
7. **Recompute after every merge.** Fetch trunk, confirm the merged SHA is present, drop the merged PR from the frozen bottom-to-top list, and run the combined post-merge checks on the new bottom PR. A host may retarget a child automatically, but do not assume it did. The only sanctioned topology change is that next PR. Retarget it to trunk through native PR editing, move its patch onto the merge result, and push with the pinned lease. Then re-run step 3. The verdict covers the patch, not its commits, so current patch evidence decides whether it survives. Merge it only once those checks pass and the verdict survives. Repeat steps 3 through 6 for that one PR. Independent work stays outside this chain and ships on its own.
8. **Watch the current frontier until it merges or fails. Do not mutate the queue around it.** Use Capy native PR/CI/review/merge notifications on the owning thread, then re-read the current PR after each event. A bundled watch-pr --status-only snapshot or gh pr view can corroborate state, but neither creates a wake subscription. Ignore READY until mergedAt is non-null or state is MERGED. Only then run step 7. Hard-fail only when `state` is `CLOSED` with no `mergedAt`, a required check concludes `FAILURE` or `CANCELLED` and blocks merge after auto-merge is no longer pending, or `mergeStateStatus` is `UNSTABLE` or `DIRTY` with no auto-merge pending. `BLOCKED` while checks are pending or auto-merge is armed is not failure. Do not use Babysit's queued `WAITING`/`merge-queue` stop condition here. Return to native event waiting when blocked. Never use a detached shell loop or Cursor `/loop`. A base that moves to trunk when its parent merges is expected, not damage to repair. Report each merge and the new ceiling. If the queue stalls, diagnose before mutating.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you armed and how you confirmed it, what landed and how you confirmed it, and what the next gap needs.
